# Ansible CI Demo

## Project Overview

This project demonstrates how GitHub Actions can automatically validate Ansible playbooks as part of a Continuous Integration (CI) pipeline.

The objective is to catch syntax and YAML formatting errors before changes are merged or deployed, helping ensure Infrastructure as Code (IaC) remains reliable and maintainable.

---

## Why Separate Workflow Files?

Instead of placing every validation step into one large workflow, each validation has its own dedicated workflow file.

This approach provides several benefits:

* Easier to read and maintain
* Simpler troubleshooting when a workflow fails
* Independent execution of each validation
* Better scalability as additional checks are added
* Follows the principle of one responsibility per workflow

As the repository grows, additional workflows can be added without making a single workflow overly complex.

## GitHub Actions Workflows

### Terraform Validation

The Terraform workflow performs:

* Repository checkout
* Terraform installation
* `terraform init`
* `terraform fmt -check`
* `terraform validate`

---

### Ansible Validation

The Ansible workflow:

* Installs Ansible on the GitHub runner
* Executes:

```bash
ansible-playbook ansible-demo/playbook.yml --syntax-check
```

This verifies that the playbook is syntactically correct without executing any tasks.

---

### YAML Validation

The YAML workflow installs **yamllint** and validates YAML files throughout the repository:

```bash
yamllint .
```

This helps identify:

* Indentation problems
* Invalid YAML syntax
* Formatting inconsistencies
* Common YAML mistakes

## Configuring `.yamllint`

During this project, a custom `.yamllint` configuration file was created to better support the repository's YAML files while still enforcing good formatting practices.

By default, `yamllint` can report warnings that are expected or acceptable in certain types of files. The custom configuration was used to reduce unnecessary warnings while continuing to catch genuine YAML issues.

The configuration includes customizations such as:

* Disabling the requirement for every YAML document to begin with `---`, since this is not commonly used in GitHub Actions workflow files.
* Configuring the `truthy` rule so GitHub Actions' `on:` keyword is treated correctly and not flagged as a boolean value, while still detecting other unintended truthy values such as `yes`, `no`, `on`, and `off` where appropriate.
* Ignoring generated directories such as `.terraform/` so downloaded providers, plugins, and generated files are not linted.
* Continuing to enforce YAML syntax, indentation, spacing, and other formatting best practices throughout the repository.

Example `.yamllint` configuration:

```yaml
extends: default

rules:
  document-start: disable

  truthy:
    allowed-values: ['true', 'false', 'on']

ignore: |
  .terraform/
```

Customizing the linter helps reduce false positives while preserving meaningful validation. This keeps CI output focused on issues that require attention instead of warnings generated by tool-specific conventions.

Syntax check the playbook:

```bash
yamllint .
```

## CI/CD Benefits

Automating Infrastructure as Code validation provides several advantages:

* Detects errors before deployment
* Prevents invalid playbooks from being merged
* Enforces consistent YAML formatting
* Provides immediate feedback after every push
* Reduces manual validation tasks
* Creates repeatable quality checks for the entire team

## Lessons Learned

Through this project I learned:

* How to validate Ansible playbooks automatically using GitHub Actions
* How `ansible-playbook --syntax-check` verifies playbook syntax without making changes
* How `yamllint` improves the quality and consistency of YAML files
* How to create a custom `.yamllint` configuration file to tailor the specific needs of the repository to filter out meaningless warnings/errors and help keep focused on meaningful output and necessary changes
